That is a claim, not a product. It is either true enough to decompile or it is not, so I built the thing that would find out, and ran it against real manufacturer documentation.

These are the notes from that. The interesting part is not that it works. It is the point where it told me it worked and was lying.

CONSTRAINT

No model in the decode path. Not for purity — for reproducibility.

A torque figure is a safety claim. If the same document can yield a different answer on Tuesday, the output is not evidence and nobody should act on it near a machine. So the extraction spine is regex, a discovered lexicon and unit-aware parsing, and the whole thing is checkable:

$ # delete every output, sever all sockets, run again $ python airgap.py data/oem/isuzu_c240.pdf airgap engaged: outbound connections raise 211 pages, tiers used: tier 1=200, tier 2=11 47 procedures, 210 steps in total 43/47 procedures ADMISSIBLE networked run : 03c8ecb52329c840256cd773929c31936c5fe263 airgapped run : 03c8ecb52329c840256cd773929c31936c5fe263 -> IDENTICAL, regenerated from scratch with no network

Byte-identical output with the network severed. That is a property a language model cannot have, and it is the whole reason for the constraint.

DESIGN

The output is an IR, so it can be checked before it is believed.

The renderer is downstream. What matters is an intermediate representation with properties a physically buildable procedure must satisfy — because the failure mode of any extraction system is confident, plausible, wrong.

PROPERTYWHAT IT RULES OUT
P1  acyclic assembly orderA machine that cannot be built
P2  referential integritySteps citing parts that were never declared
P3  no orphan partsParts that appear but are never installed
P5  provenance coverageAssertions with no span in the source
P6  torque plausibilityLost decimal points, confused units

Provenance is verified, not asserted: every span is re-located character-for-character in the page text and boxed on the rendered page. A model can claim a citation. This can be checked.

THE TEST THAT MATTERED

Fixtures I wrote passed. So I ran documents I didn't write.

A 395-page Detroit Diesel Series 53 and a 211-page Isuzu C240 workshop manual. Public domain, genuine manufacturer documentation, 1970s–90s scans with OCR text layers. Nothing authored for this project.

Three hand-made fixtures had been passing 7/7 for days. Here is what the real documents returned on the first run:

CRUCIVEX IR VALIDATION - Isuzu C240 workshop manual -------------------------------------------------------------- PASS P1 acyclic assembly order 402 steps sorted PASS P2 referential integrity 636 references resolved PASS P3 no orphan parts all 131 parts installed PASS P5 provenance coverage 533/533 verbatim (100%) PASS P6 torque plausibility no torque specs to check -------------------------------------------------------------- ADMISSIBLE: 7/7 checks passed
THE POINT OF ALL THIS

That result is worthless, and it took looking at the artifact to see it.

Every property genuinely held. The graph really was acyclic. Every reference really did resolve. Every span really was verbatim. And the artifact was a single 402-step "procedure" — on the Detroit manual, 2,120 steps — which no technician performs, because a service manual is not one job. It is two hundred jobs bound together, and I was reading the whole book as one.

A suite that only tests the properties you already thought of
will pass the failure you didn't.

Note also P6: no torque specs to check — passing vacuously on a document containing dozens of them. A green check for work not done. Both of these are the same bug class: the score agreed with me, so I nearly stopped reading.

WHAT REAL DOCUMENTS BROKE

Four bugs no fixture I wrote would ever have found.

DEFECTWHY MY FIXTURES MISSED IT
Two-column layout
Lines rebuilt by y-position zipped the columns together, so a step held half of an unrelated instruction and torques bound to the wrong step.		 I had written single-column fixtures. Real manuals are set in two.
kgf·m torque units
The parser knew N·m and lb-ft. Isuzu states every torque in kg-m — so it found zero.		 I wrote my fixtures in the units my parser knew.
Tabular torque form
Real manuals print the unit as a column header with the value on the next line, as a range.		 Scanning for "number then unit" never sees it.
HEADING_RE eating the values
A value row 2.7 - 3.3 is shaped exactly like section number 4.3, so the step was cut at the torque table.		 Every figure in the manual severed from the label naming it.
A SMALLER ONE, WORTH SAYING

I made the regex OCR-tolerant and forgot the converter.

These are scans, and OCR reads lb as Ib constantly. So I widened the unit pattern to accept it — and left the conversion function matching on lb only.

extract_torque("bolts to 12-15 Ib-ft torque") before: 12.0 N·m # matched, then fell through unconverted after: 16.3 N·m # 12 lb-ft, correctly converted

The half-fix was worse than no fix. A missing torque is a visible gap; a wrong torque is a number a technician acts on. I only caught it because I wrote the assertion table with hand-computed expected values instead of blessing whatever came out.

Widening a matcher without widening what consumes it
converts a silent miss into a confident error.
THE FIX, IN THAT ORDER

Write the check that catches it. Then fix the cause.

  • First: P8, "single procedure". A manual restarts numbering at 1 for every job, so a run of ascending numbers is one procedure and a number going backwards begins the next. More than two restarts and the document is not one procedure. Detroit restarts 407 times.
  • Then: segment on that same signal. Split the document into its constituent procedures, each decoded, checked and rendered on its own. Vocabulary stays document-wide — part names belong to the machine — but installs and dependencies scope to the procedure.

The order is deliberate. If I had only fixed the segmentation, the suite would still have been unable to detect the bug, and the next variant of it would have shipped green. The check is the part that lasts.

THE FIX HAD A COST

Segmentation silently threw away 60% of the torque specifications.

To keep spec tables and numbered notes out, I required a procedure to have at least four steps. That is a reasonable-sounding threshold and it was quietly destructive: real jobs are often two or three steps.

Isuzu C240, torque specifications: in the raw steps 20 surviving segmentation 8 # 12 lost to runs shorter than 4 steps a sample of what was being discarded (torque stated later in the run): [3 steps] Install the thrust plate -> 10.0 kg-m [2 steps] Apply engine oil to the bolt and threads -> 10.0 kg-m [3 steps] Apply a coat of engine oil to the flywheel -> 11.0 kg-m

I only found it because I was checking the numbers on these slides against the library rather than copying them forward from the previous run. A torque figure is the strongest evidence a run describes real work, so it now buys a procedure its place at a lower step count. Isuzu recovers all 20.

The fix for one bug is a good place to look for the next one.

AND THEN THE TEST WAS WRONG TOO

My first proof that it runs offline was invalid, and it passed.

To prove nothing reaches a model I replaced socket.socket with a function that raises. That breaks the ssl module at import — SSLSocket subclasses it — so the pipeline never ran at all. The hash still matched, because the previous run's files were sitting on disk.

TypeError: function() argument 'code' must be code, not str networked run : e4f68d6c...123b59 airgapped run : e4f68d6c...123b59 -> "IDENTICAL" # comparing a run that never happened

Corrected: import first, sever connect() rather than the class, assert the airgap actually raises before trusting the run, and delete every output first so a stale file cannot fake the match. Same failure I had just found in the validator, one level up.

A passing test proves the test passed.
WHAT IS STILL WRONG WITH IT

Known limits, stated before you find them.

WORKS

Tiered extraction with OCR fallback · two-column recovery · vocabulary discovered per document · dependency graph from linear prose · torque across N·m, lb-ft, kgf·m · verbatim provenance with page highlighting · eight property checks · procedure segmentation · assessed task mode with an ordering and torque record

DOES NOT

Procedure names come from the first instruction, not the section heading — I do not track heading hierarchy, and inventing a plausible title is the exact unsourced assertion this system exists to prevent · disassembly reads as assembly · pictorial-only manuals yield little · geometry is parametric, not customer CAD

Every one of those is a thing I know is broken. The list I care about more is the one I don't have — which is why the interesting work was running documents I did not author.

WHAT I ACTUALLY LEARNED

The engineering question is answered. The other one isn't, and I won't pretend it is.

Answered: a manual does carry enough structure to recover a dependency graph, torque specifications and per-procedure boundaries deterministically, with every assertion traceable to a span of the source — and it survives contact with documents written decades before the code.

Not answered: whether anyone needs this. I have no users, no customer conversations and no evidence of demand. I could construct a market argument, but it would be reasoning I have not tested, presented next to results I have — and I would rather you could tell the difference between the two.

The part of this I would defend is not the renderer.
It is that the system now refuses work it cannot justify.
